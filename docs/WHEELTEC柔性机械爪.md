## 1. STEP 能直接用吗?

**不能。** STEP 是 B-Rep 实体格式,MoveIt / Gazebo / RViz 只认三角网格
(STL / DAE / OBJ),而且 STEP 里没有"哪一块是底座、哪一块是手指"这种语义 ——
而夹爪的两片手指必须做成**两个能转的关节**,不拆开就没法张合。

所以流程是:STEP → 拆件 + 转 STL → 写 URDF 宏。转换脚本落在集成包里,
是可重跑的:

```bash
cd jaka_ros2/src/wheeltec_gripper
~/.venvs/stepmesh/bin/python tools/step_to_mesh.py     # 需要 trimesh + cascadio
```

脚本做四件事(全部有输出,改 STEP 后重跑即可):

| 产物 | 说明 |
|---|---|
| `meshes/gripper_base.stl` `gripper_jaw_l.stl` `gripper_jaw_r.stl` | 显示网格(1.5 万 / 4.9 千面) |
| `meshes/*_col.stl` | **碰撞包络**:底座 2 个盒子(24 面 —— 一个完整包围盒会把指根夹死,见 §3.2),每片指 5 段深度切片(60 面) —— 手指是锥形,用包围盒会让它"凭空变粗"撞到工件 |
| `config/gripper.yaml` | 实测几何:指尖深度、转轴坐标、开口曲线、质量与惯量 |
| `urdf/wheeltec_gripper.urdf.xacro` | 装到 `dummy_tcp` 上的宏(两个转动关节) |

## 2. 实测几何(每次重跑脚本都会核对)

从 `step/gripper.STEP` 量出来、并且和实物照片对过的关键尺寸
(单位 mm,坐标系是 `dummy_tcp`,也就是机械臂法兰面,**+z 是工具轴**,
指向夹爪外侧 —— 也就是装到机械臂上之后的"向下"):

| 量 | 值 | 为什么重要 |
|---|---|---|
| 法兰贴合面 | 0.0 | `dummy_tcp` 原点 = 机械臂法兰面;夹爪的 63×63 转接板贴在这个面上 |
| 掌底(底座/电机最低点) | 83.5 | 工件顶面必须低于它,再往上就顶到电机了 |
| 指根转轴 | (±35.2, 0, 82.9) | 两片指的转动中心,轴平行于 ±y |
| **指尖深度** | **164.6** | **最要紧的一个数**:工件是夹在两片指之间的,抓取高度由它定 |
| 张开净距(在 120.3 深处) | 70.3 | 最大能夹多宽 |
| 闭合速率 | 1.303 mm/° | 指间净距每闭合 1° 少这么多 |
| 关节行程 | 0 … 35.9° | 再合两片指就互相干涉 |
| 可夹工件宽度 | 24 … 70 mm | 由上面两个数推出来 |
| 质量 | 底座 300 g + 每片指 35 g | 惯量按凸包算,已写进 URDF |

> **+z 还是 -z 曾经搞错过一次,值得记一笔。** 机械臂的 `Link_6` 网格铺在
> `z ∈ [-39, 0]` 上,一开始被误读成"法兰面在 z=-40,夹爪从那里往下装",于是
> 整只爪子被翻过来、又往小臂里推了 40mm —— 指尖深度也连带记成了 204.6mm。
> 正确的读法是:`Link_6` 和 `dummy_tcp` 同一个原点,臂的材料**整个在 -z 一侧**,
> 所以 z=0 就是法兰贴合面,工具只能往 +z 装。换成 `arena.yaml` 的
> `tool_down_quat`(绕 X 转 180°)之后,TCP 的 +z 正好指向世界下方 ——
> 这也是"J5 在 TCP 正上方 159.3mm"那条可达性公式成立的前提。

## 3. 怎么用

### 3.1 仿真(Gazebo / RViz)

整只夹爪(URDF + 抓取高度 + 控制器)由**一个环境变量**切换:

```bash
JAKA_GRIPPER=1 ros2 launch jaka_competition_kit round.launch.py \
    world:=gazebo track:=1 seed:=246135
```

不设这个变量 = 规则书要求的那种"裸法兰 / 行程几十毫米的小平行夹爪"。

这个变量同时管三处,**不存在只改一半的组合**:

| 被它切换的东西 | 具体位置 |
|---|---|
| URDF 里挂不挂夹爪 | `jaka_minicobo.urdf.xacro` 的 `with_gripper`(读同一个变量) |
| 抓取/转场/投放高度 | `jaka_competition_kit/config/arena.yaml` 的 `tool.gripper` |
| `gripper_controller` 起不起 | `round.launch.py` 的 `use_gripper`(默认跟着变量走) |

仿真里两片指是 `ros2_control` 的 `JointGroupPositionController`(关节名
`gripper_jaw_l_joint` / `gripper_jaw_r_joint`)。两片的关节轴**都是 +y**(用负向轴
会让 Gazebo 把关节冻住,详见 URDF 里的说明),所以"往中心合"的符号**相反**:
**闭合 = 左指出负角、右指出正角**,想让手合到 50mm 净距就发 `[-0.22, 0.22]`。

```bash
ros2 topic pub --once /gripper_controller/commands \
    std_msgs/msg/Float64MultiArray "{data: [-0.22, 0.22]}"  # 左负右正 = 闭合; 0.22 rad ≈ 12.5° ≈ 夹 50mm
ros2 topic pub --once /gripper_controller/commands \
    std_msgs/msg/Float64MultiArray "{data: [0.0, 0.0]}"      # 张开(两指都回原位)
```

比赛流程里不用手发:`SimGripper` 会按工件实际宽度把角度算出来
(`arena.yaml` 的 `jaw_gap_open` / `jaw_gap_per_deg` / `jaw_limit_deg`)——
真机靠堵转自停,仿真没有这回事,不按尺寸收手指会直接穿过工件。

### 3.2 Gazebo 里的三个坑(手指不动时先看这里)

柔性爪在仿真里"发什么命令都不动"踩过三次,原因都不在控制器,而在 URDF / 碰撞体:

1. **关节轴不能用负向向量。** 原来把 +x 侧的指写成 `<axis xyz="0 -1 0"/>`(想用
   轴的方向直接表达左右镜像),`ign_ros2_control` / Gazebo 会**把这个关节冻死** ——
   实测同一套模型只把轴从 +y 换成 -y(位姿、碰撞体、行程都没变),不管下发 +0.45
   还是 -0.45,两个关节都纹丝不动。改回"两片轴都是 +y,左右靠命令符号区分"就正常了。
2. **行程不能正好卡在静止位上。** 原来写 `<limit lower="0" upper="limit"/>`,而模型
   原状(张开)就是 0 —— 关节正好压在行程边界上,Gazebo 同样不动。现在写成对称的
   `[-limit, +limit]`,0 落在行程中间。(往外张没有物理意义,真机螺杆本来就带不动。)
3. **底座碰撞体不能跨过指根。** STEP 里指根本来就插在机架里(装配体本来是穿模的),
   如果底座的碰撞用一个完整包围盒,Gazebo 会把这条"指根与机架互相嵌入"当成硬接触
   把手指顶死。现在底座拆成两个盒子:下半段(转接板/电机)完整,指根高度那一段只留
   中间的机架、两侧让给手指扫掠 —— 见 §1 的表格和 `tools/step_to_mesh.py` 的
   `base_boxes()`。

排查这类问题别只看 MoveIt 的 `error_code`,直接读关节真值:命令下发后看
`/joint_states` 里 `gripper_jaw_l_joint` / `gripper_jaw_r_joint` 有没有跟着变。

### 3.3 真机

```bash
# 1) 串口权限(插拔一次即可,规则写的是 /dev/motor_serial)
#    脚本里的 ATTRS{serial}=="56B8006534" 是厂商那根线的序列号:
#    换线要改成自己的(udevadm info -a -n /dev/ttyACM0 | grep serial),
#    或者干脆把那个条件删掉 —— 只按 USB VID/PID 认也行
sudo bash jaka_ros2/src/step_motor/ch9102_udev.sh

# 2) 起驱动
ros2 run step_motor motor_node            # 参数: usart_port_name=/dev/motor_serial
                                          #       serial_baud_rate=115200

# 3) 队伍代码里把夹爪切成真机驱动
ros2 launch jaka_competition_kit round.launch.py ... gripper:=wheeltec
# 或者参考实现单独跑: ros2 run jaka_competition_kit ref_track1 --ros-args -p gripper:=wheeltec
```

协议(厂商《驱控一体步进电机 ROS 控制使用手册》,实现见
`step_motor/src/motor_node.cpp` 与 `jaka_competition_kit/gripper.py` 的
`WheeltecGripper`):

| 项 | 值 |
|---|---|
| 话题 | `/motor_control`(`step_motor/msg/Motor`)→ 电机; `/motor_state` 回读 |
| 帧格式 | `7B` … `7D` + BCC(异或校验),帧长 11 字节 |
| `mode` | 2 = 相对角度模式(本项目只用这个) |
| `angle` | 相对转角,**放大 10 倍**发送(`0.1°` 为单位) |
| `dir` | 0 = 逆时针 = **张开**,1 = 顺时针 = **闭合** |
| `sub_divide` | 32(细分,越大越平滑) |
| `speed` | 放大 10 倍,单位 0.1 rad/s |
| 行程 | 全闭合 5.2 圈 ≈ 1872°;**顶到工件会堵转自停**,所以"发一个够大的角度"就是"夹紧" |
| 保护 | 堵转保护 + 输入反接保护(不支持热插拔) |

`dir` 的方向约定来自实物:闭合 = 顺时针。如果接线后方向反了,把
`WheeltecGripper` 的 `dir` 对调即可,不用改协议。

## 4. ⚠ 可达性:这只夹爪改变了"哪里够得到"

**这是本次集成最需要知道的结论。**

机械臂末端能不能到,取决于一个很简单的几何:工具轴竖直向下时,
`J5` 一定在 TCP 正上方 `wrist_len=159.3mm` 处(推导见
`Arena.max_tcp_z` 的注释,依据是 URDF 里 `joint_6` 的偏移方向与 Link_6 的
`rpy=-90°`),而 `J5` 必须落在以 `J2` 为心、`大臂+小臂=420.5mm` 为半径的球内。于是

```
r² + (z + 159.3 - 187.0)² ≤ 420.5²          (单位 mm)
=>  z_max(r) = 27.7 + sqrt(420.5² - r²)
```

用 40 个随机种子打 `/compute_ik` 实测(每次都是"全中 / 全不中"的硬边界,
和公式完全吻合):

| 半径 r | 公式上限 | 实测 |
|---|---|---|
| 355.0 mm | 253.1 mm | z=248.6 全中 |
| 362.8 mm(料盒中心) | 240.3 mm | z=240 全中 / z=245 全不中 |
| 385.4 mm(工位 4/6) | **195.9 mm** | z=195 全中 / z=200 全不中 |

而换上柔性夹爪之后,`grasp_tcp_z` 从 **100.0mm 抬到 173.6mm**
(工件顶面 54mm + 指尖深度 164.6mm + 刀尖余量 5mm − 工件高 50mm)——
比 `gripper: none` 那颗假想的 40mm 小夹爪整整高 73.6mm。逐点对一下:

| 目标 | r | 需要的 z | 该半径上限 | 结果 |
|---|---|---|---|---|
| 工位 1/2/3 抓取、预抓取 | 205–254 | 173.6 / 208.6 | 362.8 / 394.8 | ✔ 余量充足 |
| 工位 5 抓取、预抓取 | 355.0 | 173.6 / 208.6 | 253.1 | ✔ 预抓取只剩 44.5mm |
| 工位 4/6 抓取 | 385.4 | 173.6 | **195.9** | ✔ 只剩 22.3mm |
| **工位 4/6 预抓取** | 385.4 | 208.6 | **195.9** | ✘ 差 12.7mm |
| 料盒中心 转场 | 362.8 | 232.6 | **240.3** | ✔ 只剩 7.7mm |
| 料盒中心 投放 | 362.8 | 189.6 | 240.3 | ✔ |

> 这张表是按"工具轴竖直向下、末端正好落在该点"算的严格判据。两行 ✘ 都出在
> **工位 4/6**: 预抓取悬停高 12.7mm, 夹起来之后要竖直抬到的转场高度高 36.7mm。
> 两条都不用改布局 —— 悬停只是个余量, 压到该半径上限即可; 转场高度按下面的
> **L 形转场**绕开(见下节)。

随时可以重新打印这张表:

```bash
JAKA_GRIPPER=1 ros2 run jaka_competition_kit arena_check
```

> 2026-09 实测(`JAKA_GRIPPER=1` 在 Gazebo 里跑一整轮赛道一, 种子 246135):
> 直接打 `/compute_ik` 复核过 r=385.4mm 这条竖直轴: **z ≤ 195.9mm 有解,
> z ≥ 200mm 全部无解**(200 / 208.6 / 220 / 232.6 都是 `error_code=-31`),
> 与公式上限 195.9mm 完全一致。也就是说工位 4/6 的**预抓取点(208.6mm)和
> 转场高度(232.6mm)都根本没有逆解**, 抓取点(173.6mm)有解。
>
> 修好之后跑一整轮: **6 个工位全部入盒、顺序正确、69.6s、100.0 分**
> (限时 145s)。这正是"不发够不到的指令 + L 形转场"两处改动的验收结果。
>
> 改之前的行为值得记一笔, 因为它就是"抓取放置的解算看起来很怪"的来源:
> 预抓取点(208.6mm)没有逆解时, 参考实现会退化成"只给位姿目标"的兜底模式 ——
> **规划器于是随机挑了一组关节解**, 实测挑到了 `J4=±180°/ J5 反号 / J6=±180°`
> 的腕部另一支: 第一件还是正常位形(J4=0), 从第二件起整条手臂都翻着腕走,
> 而且失败重试会在 `J4=-180° → 0° → +180°` 之间来回翻 —— 每翻一次全臂绕 180°,
> 单件白跑 30s。现在实测整轮 **`J4` 恒为 0**, 腕部一次都没翻。

### 4.1 L 形转场: 竖直抬不到就"先抬 -> 内收 -> 再抬"

`z_max(r)` 只跟**水平半径**有关, 所以"原地抬不到转场高度"不是死路: 朝基座收一点,
同样高度就够得着了。以工位 4/6(r=385.4mm)为例:

| 段 | 动作 | 半径 | 该半径上限 |
|---|---|---|---|
| ① | 原地竖直抬到 195.9mm(该半径的上限) | 385.4 | 195.9 |
| ② | 沿**半径方向**朝基座内收到 r=361mm | 385.4 → 361 | 195.9 → ≥256 |
| ③ | 再竖直抬到转场高度 232.6mm | 361 | ≥256 |
| ④ | 直线转场到料盒(工件底面已高于全场最高件) | ≤361 | ≥256 |

为什么第 ② 段可以贴着台面横着走: **6 个工位都在同一圈上, 沿半径内收不会经过
任何邻件** —— 实测工位 4 的内收路径离最近邻件中心 138mm(工件半宽 25+25=50mm
就够), 工位 6 同理。而第 ② 段只在"还没抬够高度"时才需要; 一旦抬到转场高度,
工件底面就比全场最高的工件(53mm)还高 10mm, 第 ④ 段横穿赛场是安全的。

实现: `Executor.pick_and_place` 先比 `tz` 与 `reach_top_z(x, y)`, 够不到才走这条
三段路径; 内收目标半径由 `Arena.radius_for_tcp_z()` 反算(留 `reach_pull_margin`
的余量)。够得到时**仍然是原来的一步竖直抬升** —— 短末端与近端工位不受影响
(默认 `gripper: none` 实测仍是 100.0 分 / 49.0s)。

### 想让它跑通,可选的路

| 方案 | 说明 | 代价 |
|---|---|---|
| **换回短夹爪**(当前默认) | 规则书写的就是"电动平行夹爪,行程 0–30mm",和裸法兰差不多长 | 不用这只柔性爪 |
| **把工位阵内移** | `arena.yaml` 的 `array_center_r` 从 280 改到 ≈250:远端工位 r 从 385→355,`z_max` 195.9→253.1,4/6 的预抓取(208.6)和转场高度(232.6)就都在范围内了 | 赛场布局变了,`competition.md` / `赛题细则` / 配图要同步改 |
| **先内收再抬高**(**已实现**, 见 §4.1) | 竖直抬升之所以失败, 是因为那条直线整段都在 r=385mm 上。先沿**半径方向**朝基座收 ≈25mm, 再抬到 232.6mm —— r 掉到 367mm 以下就够得到了 | 已落在参考实现里(`Executor.pick_and_place`); 内收段是"还没抬够高度"时唯一的水平移动, 只能走半径方向, 换布局要重新算邻件间距 |
| **倾斜手腕下抓** | 绕工具轴先转 90°(让两片指沿切向张合),再向基座方向倾 15–20°:`J5` 沿刀尖方向内收 `159.3·sinθ`,r=385 处 `z_max` 能从 195.9 提到 240 以上 | 抓取姿态、附着位姿、预抓取点都要重算;两片指不再水平,夹锥形/薄件时接触会变 |

当前仓库默认仍是不装柔性爪(`gripper: none`)—— 规则书要求的就是行程 0–30mm 的
电动平行夹爪。柔性爪的模型、驱动、参数都在, `JAKA_GRIPPER=1` 挂上去现在也能跑完整
一轮赛道一(6/6, 100.0 分), 可以直接拿来做演示或二次开发。

## 5. 常见问题

**Q: `ros2 launch ... round.launch.py gripper:=wheeltec` 之后夹爪不动?**
`motor_node` 起了吗(`ros2 run step_motor motor_node`)?串口开了吗
(`/dev/motor_serial`)?另外 `ref_track1` 的 `gripper` 参数与 `use_gripper`
互相独立:仿真用 `sim`,真机用 `wheeltec`。

**Q: 仿真里两片指纹丝不动(发命令没反应)?**
见 §3.2:关节轴写成负向向量、行程卡在静止位、底座碰撞体跨过指根,三者都会让手指
在 Gazebo 里被冻住。用 `/joint_states` 确认关节有没有真的动。

**Q: 仿真里手指穿过工件?**
说明 `SimGripper` 不知道工件尺寸(传了 `None`),它会把手指合到底。
检查是不是绕过了 `Executor.grasp()` 直接调了 `gripper.close()`。

**Q: Gazebo 里夹爪是隐形的(但 RViz 里看得见)?**
新加的网格包必须在 `package.xml` 里导出 `<gazebo_ros gazebo_model_path="${prefix}/.."/>`
(`wheeltec_gripper` 与 `jaka_description` 都导出了)。Gazebo 不认 `package://`,
`ros_gz_sim` 把它转成 `model://<包名>/...` 之后只在 `GZ_SIM_RESOURCE_PATH` 里找,
而这条路径**只收声明了该导出的包**。漏掉时的现象是 Gazebo 启动日志里刷
`Unable to find file with URI [model://wheeltec_gripper/meshes/...]`,
**显示网格和碰撞体一起加载失败** —— 夹爪看不见, 而且不参与物理接触
(手指会直接穿过工件)。改了 `package.xml` 要重新 `colcon build` 再起仿真。

**Q: 机械臂带着夹爪做抓取/放置时"翻腕"、动作很怪?**
那是**目标点超出可达范围**的典型症状, 不是规划器抽风: 够不到的位姿
`/compute_ik` 会给"无解", 参考实现就退化成"只给位姿目标"的兜底模式, 而
**规划器会在同一姿态的多组关节解里随机挑一支** —— 实测挑到了 `J4=±180°`、
`J5` 反号、`J6=±180°` 的腕部另一支, 于是整条手臂翻着腕走; 失败重试还会在
`J4=-180° → 0° → +180°` 之间来回翻。
现在参考实现不会下发够不到的目标: 预抓取悬停压到该半径上限(见
`Arena.clamp_tcp_z`), 转场高度够不到就走 L 形(§4.1)。整轮 `J4` 恒为 0。
用 `JAKA_GRIPPER=1 ros2 run jaka_competition_kit arena_check` 可以核对每个
目标的高度与该半径的上限。

**Q: 机械臂带着夹爪"莫名其妙规划失败"?**
先看是哪一类:`JAKA_GRIPPER=1 ros2 run jaka_competition_kit arena_check`
会打印每个目标的可达上限。MoveIt 对"撞了"和"根本到不了"都只回一个
`error_code=99999`,光看返回值分不出来,所以工具包把这条几何算成了公式。

**Q: 夹爪开口是 70mm,能夹 70mm 的工件吗?**
不能夹满。24–70mm 是"指间净距"的范围,工件要留一点缝(仿真里是
`jaw_gap_extra`,默认 4mm),而且指间净距随深度变化(上宽下窄),
梯形/锥形工件会卡在某个深度上 —— 这正是"柔性"爪的自适应夹持方式。

**Q: 厂商资料里那两个夹爪尺寸(98×113×153mm / 72×64×100mm)和这里对不上?**
那是《柔性机械爪开发手册》(舵机版)里另外两个型号的标称外形。
本仓库用的是 `gripper.STEP` 实测值:法兰以下总高 164.6mm、张到最大时
最宽 117.8mm,与随资料附带的 `2.三维模型/gripper.stp` 是同一只夹爪的
不同版本导出。
